1. Сплошное чтение исходников: `src/*.js` (16 модулей), `native/*.c|h`, `bin/`, `bench/`, `test/`, `spec/`, `SECURITY.md`.

**Главный вывод.** Криптографическое ядро (macaroon-цепочки, доменное разделение, C11-примитивы, санитайзинг заголовков, защита от smuggling) сделано **действительно хорошо и добротно** — это уровень выше типичного pet-проекта. Differential fuzzing C↔JS, ASan/UBSan в CI, честный самокритичный бенч — сильные стороны, которые стоит показывать.

Но **слой принятия решений о лимитах (Limiter) построен на данных, которые приходят от атакующего**. Три из четырёх «уровней защиты» (H-1, H-3, H-8) обходятся одним заголовком. Это не частная ошибка, а системная: identity подменяется на client-controlled input там, где должна быть верификация. Отсюда главный архитектурный совет (§6).

Второе: **PoE/`h4-pass` — головная фича в README — по умолчанию отключена и не может включиться**, потому что `pressure` нигде не подключён к реальному сигналу (M-2).

## 2. Подтверждённые уязвимости (с PoC)

### H-1 · Подмена анонимной квоты через `h4-agent-instance` — ВЫСОКАЯ ✅ ИСПРАВЛЕНО

**Было** (`src/server.js:771`):
```js
_subjectFromRequest(peerNorm, h) {
  const inst = h['h4-agent-instance'] || h['h4-agent'] || '';   // ← из заголовка запроса
  return sha256(`${inst}|${net}`).slice(0, 16);
}
```
Ключ персональной квоты для **неаутентифицированного** вызывающего содержал значение из его же заголовка. Меняя его на каждый запрос, клиент получал свежий бакет.

`poc/01-subject-rotation.mjs`, `budget: 20`:

| | до | после |
|---|---|---|
| честный клиент | 20 / 200 | 20 / 200 |
| с ротацией заголовка | **80 / 200** | **20 / 200** |
| создано бакетов в Limiter | **200** | **1** |

Реальный потолок для анонима — не `budget`, а `budget × netMultiplier` (по умолчанию ×4). Плюс неограниченный рост `Limiter.entries` → см. H-2.

**Исправление:** анонимный subject выводится только из IP. `h4-agent-instance` теперь может лишь *дробить* уже верифицированную идентичность.

---

### H-2 · Алгоритмический DoS: `Limiter._gc()` — ВЫСОКАЯ ✅ ИСПРАВЛЕНО

**Было** (`src/limits.js`): полный O(n)-проход по карте **на каждую вставку** после насыщения (200k).
```js
if (this.entries.size >= 200000) this._gc(now);   // _gc() итерирует всю карту
```
Ключ subject контролируется атакующим (H-1) ⇒ насытить карту тривиально.

`poc/02-limiter-gc-blowup.mjs`:

| | до | после |
|---|---|---|
| 200 000 уникальных субъектов | 204 мс | 181 мс |
| следующие 5 000 запросов | **14 888 мс (2 978 мкс/запрос)** | **31 мс (6,2 мкс/запрос)** |
| амплификация | **×2 925** | ×7 |

Падение с ~1 000 000 проверок/с до ~336/с на одном ядре, постоянно, пока идёт атака.

**Исправление:** не более одной полной чистки на окно + O(256)-сброс самых старых ключей между чистками (JS `Map` сохраняет порядок вставки).

---

### H-3 · Подмена агрегатной квоты через `CF-Connecting-IP` — ВЫСОКАЯ ✅ ИСПРАВЛЕНО

**Было** (`src/adapters.js:50`):
```js
const peer = envOrCtx?.remoteAddress ?? rawHeaders['cf-connecting-ip'] ?? 'web-edge';
```
`rawHeaders` = `Object.fromEntries(request.headers.entries())` — то есть **заголовки запроса**. `SECURITY.md §4.3` обещает, что peer «намеренно игнорирует недоверенные X-Forwarded-For» — но это ровно тот же класс ошибки, только с другим именем заголовка.

`poc/04-peer-spoof.mjs`, `budget: 5`, `netMultiplier: 4`:

| | до | после |
|---|---|---|
| фиксированный IP | 5 × 200, 55 × 429 | 5 × 200, 55 × 429 |
| ротация заголовка | **60 × 200, 0 × 429** | **5 × 200, 55 × 429** |
| создано net-бакетов | 60 | 1 |

Обходятся **оба** уровня сразу: и персональный, и агрегатный.

**Исправление:** `envOrCtx.remoteAddress` → `request.cf.connectingIp` (инъектируется рантаймом Workers, клиентом не пишется) → `'web-edge'`.

### H-4 · Sidecar раздаёт ответ одного пользователя другому — ВЫСОКАЯ ⚠️ НУЖНО РЕШЕНИЕ

Ключ кэша (`src/server.js:617`):
```js
const vary = [h['h4-cache-key'] ?? '', h['accept'] ?? '', tenantTag, String(intent.maxShape ?? 0)];
return this.cache.key([method, rawPath, ...vary, bodyHash, intent.dedup ?? '']);
```
В ключе **нет** `cookie`, `authorization`, `x-api-key`, `range`. У неаутентифицированного вызывающего `tenantTag` — константа `anon:`. `Cache-Control: private/no-store` от апстрима полностью игнорируется.

Это бьёт ровно по «главной» интеграции из README — `npx http4 proxy --upstream ... --ttl-ms 5000`.

`poc/03-sidecar-cache-user-confusion.mjs` (апстрим отвечает `Cache-Control: private, no-store`):
```
alice -> {"user":"alice","secret":"api-key-of-alice"}
bob   -> {"user":"alice","secret":"api-key-of-alice"}   *** LEAK ***
carol -> {"user":"alice","secret":"api-key-of-alice"}   *** LEAK ***
upstream was actually called 1 time(s) for 3 distinct users
```

**Почему не правлю сразу:** это продуктовое решение. Варианты: (a) не кэшировать запросы с `Cookie`/`Authorization` при `tenantTag === 'anon:'`; (b) уважать `Cache-Control`/`Vary` апстрима; (c) вынести политику в опцию. Все три меняют поведение по умолчанию — нужно выбирать осознанно. Склоняюсь к (a)+(b).

### H-5 · `h4-pass` «одноразовый» → многоразовый — ВЫСОКАЯ ✅ ИСПРАВЛЕНО

**Было** (`src/privacy-pass.js`): таблица двойного расходования вытеснялась по **FIFO по счётчику**, а не по сроку жизни:
```js
if (this.redeemed.size >= this.maxRedeemed) this.redeemed.delete(FIRST key);
```
`#pruneExpired` просматривал всего 64 записи за вызов ⇒ при реальной нагрузке таблица всегда упиралась в кап и начинал работать FIFO, забывая **ещё живые** пассы.

`poc/05-pass-doublespend.mjs`: `redeem #3` → `{"ok":true,...}` — пасс принят повторно.

**Исправление:** полная чистка по сроку жизни, затем **fail-closed** (`why: 'pass-table-full'`). Таблица одноразовости обязана отказывать, а не забывать. PoC теперь завершается с `exit 1`, только если уязвимость жива.

---

### H-6 · Идемпотентность уничтожается удалённо → двойное списание — ВЫСОКАЯ ⚠️ НУЖНО РЕШЕНИЕ

**Было** (`src/server.js:455`): одна глобальная карта на 10 000 записей; ключ содержит subject, а subject для анонима управлялся клиентом (H-1).
```js
if (this.idemStore.size >= 10000) this.idemStore.delete(this.idemStore.keys().next().value);
```

`poc/06-idem-eviction.mjs`:
```
alice sends order-42 twice -> charges = 1        (идемпотентность работает)
idemStore size after flood : 10000
alice retries order-42     -> charges = 10052    (было 10051)
*** IDEMPOTENCY DESTROYED: тот же Idempotency-Key выполнил мутацию повторно ***
```
Т.е. легитимный ретрай того же `Idempotency-Key` после флуда **выполняет списание второй раз**. Для платёжного API это деньги.

**Почему не правлю сразу:** фикс H-1 снимает дешёвый вектор (ротация subject), но глобальная карта с вытеснением по счётчику всё равно остаётся гонкой за место между арендаторами. Нужно либо шардировать по tenant, либо давать гарантию «не вытеснять живые записи, иначе fail-closed» (как в H-5), либо выносить в Redis. Это уже про многопользовательскую модель — см. §6.

---

### H-7 · Replay nonce'ов PoE после насыщения `usedPoe` — СРЕДНЯЯ ✅ ИСПРАВЛЕНО

Тот же антипаттерн, что H-5: `src/limits.js` вытеснял FIFO-запись из **живого** 30-секундного окна, перезаряжая уже использованный nonce. Исправлено на «чистка по окну + fail-closed».

---

### H-8 · `maxSubs` не проверяется нигде — СРЕДНЯЯ ⚠️ НУЖНО РЕШЕНИЕ

`SECURITY.md §1` прямо перечисляет угрозу «fan out into thousands of instances». Проверки нет: `maxSubs` подписывается в root grant, но сервер его ни с чем не сравнивает.

`poc/07-fanout-and-class.mjs`:
```
root grant said maxSubs=2; we minted 500 live sub-agents
all 500/500 were admitted; distinct limiter buckets created = 500
shared grant ('net') allowance = budget*(1+bonus)*maxSubs = 1200,
yet each sub-agent ALSO gets its own 600-unit bucket and maxSubs is never counted.
```
Один утёкший root с `maxSubs=4096` ⇒ до `4096 × 600 = 2.46M` запросов / 10 с.

**Почему не правлю сразу:** чтобы считать fan-out, нужен серверный счётчик на `grant` с TTL — то есть новое состояние с новой политикой вытеснения (и всё те же грабли H-5/H-7). Нужно решение.

## 6. Архитектурный диагноз

Почти все HIGH-находки — не случайные опечатки, а проявление одного принципа:

> **Идентичность, используемая для принятия решений о лимитах, берётся из тех же данных, что и атака.**

- subject анонима ← заголовок (H-1)
- peer ← заголовок (H-3)
- ключ кэша ← `h4-cache-key`/`h4-tenant` при `anon:` tenant (H-4, M-6)
- fan-out ← ничем не ограниченный `maxSubs` (H-8)
- «стоимость» запроса ← `cost.costClass` клиента

Правило, которое стоит зафиксировать в `CONTRIBUTING.md`:

> **Invariant:** любой ключ, по которому принимается решение о допуске/кэше/идемпотентности, должен быть либо криптографически верифицирован, либо производным от адреса. Ни один client-controlled заголовок не имеет права попадать в ключ без проверки.

Второй системный момент: **все четыре таблицы состояния сервера используют FIFO-вытеснение по счётчику** (`entries`, `netEntries`, `usedPoe`, `redeemed`, `revokedGrants`, `idemStore`). Для таблиц, которые *обеспечивают* гарантию (анти-replay, одноразовость, отзыв, идемпотентность), вытеснение = **тихая потеря гарантии**. Там единственная корректная политика — **fail-closed**.
