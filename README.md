# HTTP/4 — reference implementation

> Агент-нативный, экономически осознанный, устойчивый к атакам наследник HTTP.
> Спецификация: **[spec/http4.md](spec/http4.md)** ← начинать надо с неё.

Это не ещё один «HTTP/3 с бантиком». HTTP/4 меняет три вещи: запрос несёт
**намерение и цену**, идентичность — это **capability-токен с офлайн-делегацией**,
а лимиты считает **не только сервер, но и клиент** — поэтому честный клиент
останавливается до того, как серверу придётся защищаться.

```
$ node test/run.js
62 passed, 0 failed

$ node demo.js
…
   honest requests served          classical      http/4
                                    300 (12.0%)   2500 (100.0%)
   attacker served                 2100 (12.0%)    400 ( 2.3%)
```

## Установка и запуск

Нужен только Node.js ≥ 20. Зависимостей нет.

```bash
node test/run.js            # 62 инварианта; каждый соответствует разделу спеки
node demo.js                # end-to-end по реальному TLS 1.3 (ALPN h4), 7 сценариев
node bench/bench.js         # размеры на проводе, кодек, примитивы, экономика PoE
node bench/attack-sim.js    # сравнение collateral damage по-честному
```

## Что внутри

| Файл | О чём |
|---|---|
| `src/varint.js` | кодирование целых, QUIC-совместимое (RFC 9000 §16, до 62 бит + безопасный zigzag) |
| `src/headers.js` | статическая таблица под агентов, префиксный словарь значений, интернирование |
| `src/frames.js` | 14 типов кадров: `HELLO`, `INTENT`, `COST`, `CAP`, `RESULT`, `RATE`, `REJECT`, `ACCESS` |
| `src/identity.js` | capability-токены (macaroon-стиль), подписанный `maxSubs`, офлайн-сужение прав, кэш проверки |
| `src/limits.js` | три ступени: кооперативная квитанция → per-identity bucket → одноразовый proof-of-effort |
| `src/cache.js` | tenant-изолированный LRU + coalescing (100 одинаковых запросов = 1 вычисление) + SWR |
| `src/server.js` | порядок проверок от дешёвых к дорогим, `deadline_ms`, `idem`, обучение оценке стоимости |
| `src/client.js` | честный учёт бюджета, онлайн-обучение по `cost_asym`, самоблокировка |
| `src/wire.js` | QUIC-нумерованные потоки + `F.HELLO` поверх TLS 1.3 с `ALPN h4` |
| `src/gateway.js` | edge-гейтвей HTTP/1.1 и HTTP/2 ↔ HTTP/4 (`Alt-Svc`, `Bearer` capability, `RateLimit-*`) |
| `spec/http4.md` | **главный документ**: дизайн, обоснования, измерения, журнал ошибок |

## Ключевые измеренные числа

Всё на 2 vCPU / Node 22, воспроизводимо через `bench/`.

| | |
|---|---|
| простой GET на проводе | **12 байт** (HTTP/1.1: 72) |
| агентский запрос, 8 заголовков | **48 байт** (HTTP/1.1: 200) |
| кодирование 8 заголовков | 1.7 µs |
| проверка capability (кэш корня, 2 хопа) | 15 µs |
| лимит по квитанции | 5 µs · по bucket — 0.1 µs |
| обслужить запрос | 15.3 µs (65k req/s/ядро) |
| отказ | 7.0 µs (в 2.2× дешевле обслуживания) |
| PoE: сложность 20 бит | атакующий 2.1 s CPU · защита 2 µs |

## Три идеи, которые всё держат

**1. Цена — часть протокола.** `INTENT` объявляет намерение и потолок, `COST` —
предсказание, `RESULT` возвращает факт и **асимметрию** с предсказанием. Последнее
превращает предсказание цены в обучаемую систему без центрального координатора.

**2. Делегация без сети.** Ed25519 один раз на грант (кэшируется), дальше только
HMAC по цепочке. Суб-агент получает суженный токен офлайн, за микросекунды.
Расширение прав невозможно — отклоняется на верификации.

**3. Клиент — участник защиты.** Сервер выдаёт квоту и сессионный ключ; клиент
ведёт учёт и сам себя блокирует. Исчерпавший бюджет клиент просто перестаёт
отправлять — отбивать нечего. Не играет по правилам? Жёсткий bucket. Перегрузка?
Не бан, а **цена** в битах.

## Совместимость

Gateway-first: H3 остаётся, H4 говорит напрямую, легаси подключается через
edge-переводчик H3↔H4. Формальные фазы внедрения — §10 спеки.

## Ограничения этого репозитория

- Транспорт — TLS-over-TCP с явным конвертом, **не** настоящий QUIC (в песочнице
  нет UDP-стека). Семантика от этого не зависит: `src/wire.js` — единственный
  файл, знающий про транспорт.
- PoE-сложность — эвристика, не модель (открытый вопрос §12).
- Инвариант «сужение только вниз» покрыт тестами, но не формальной верификацией.
