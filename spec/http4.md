# HTTP/4 — спецификация, дизайн-обоснование и reference-реализация

**Черновик 0.1 · ноябрь 2026 · статус: экспериментальный**

| | |
|---|---|
| Транспорт | эволюция QUIC (мультиплексирование, 0-RTT, миграция соединений — не переизобретаем) |
| Совместимость | gateway-first: H3 остаётся, H4 говорит напрямую, легаси подключается через edge-переводчик |
| Ключевая идея | запрос перестаёт быть «сообщением», становится **транзакцией с объявленной ценой, подтверждённой идентичностью и взаимными обязательствами сторон** |
| Безопасность | слоёная, но дешёвая: цена проверки ≤ 15 µs, отказ дешевле обслуживания в 2.2×, всё, что дорого, вынесено с горячего пути |
| Реализация | `src/` — 10 файлов, 62 инварианта, воспроизводимые бенчмарки |

Этот документ — не RFC «на подпись», а работающий проект: каждое утверждение ниже либо доказано тестом, либо измерено в `bench/`. Там, где мы ошиблись по ходу разработки, ошибки не спрятаны, а описаны в §11.

## 0. TL;DR — что предлагается

HTTP/4 меняет три вещи и только три.

1. **Запрос несёт намерение и цену, а не только метод и путь.** Клиент обязан объявить, *что* он делает (`INTENT`: запрос / мутация / подписка, дедлайн, ключ идемпотентности) и *сколько это может стоить* (`COST`: предсказание, класс, потолок). Сервер обязан вернуть *фактическую* стоимость (`RESULT.cost_actual`) и *асимметрию* с предсказанием. Это превращает интернет из «бесплатных запросов» в рынок с обратной связью, и именно этой обратной связи не хватает для агентов.

2. **Идентичность — это capability-токен, который можно сужать офлайн.** Агент, порождающий суб-агентов, не должен ходить в auth-сервис на каждый хоп. H4 даёт macaroon-подобную делегацию: Ed25519 подпись один раз на грант (кэшируется), дальше только HMAC по цепочке. Сужение прав невозможно обойти, расширение — отклоняется.

3. **Лимиты считает и клиент.** Сервер выдаёт клиенту квоту и сессионный ключ; клиент ведёт честный учёт и **сам себя блокирует до отправки**. Запрос, который не будет обслужен, вообще не должен появляться в сети — ни для сервера (он дешевле), ни для клиента (он быстрее), ни для всех остальных (меньше объём атаки). Если клиент не играет по правилам — сервер переключается на жёсткий per-identity bucket, а при перегрузке не банит, а **назначает цену** (proof-of-effort).

Всё остальное — сжатие заголовков, кэш, фреймы, коды отказа — обслуживает эти три идеи.

## 1. Задача и ограничения

### 1.1 Что изменилось в интернете к 2026

| Тренд | Следствие для протокола |
|---|---|
| Большинство трафика — не люди, а агенты и пайплайны | Заголовки становятся машиночитаемыми и повторяющимися; User-Agent бесполезен, нужна проверяемая идентичность |
| Запрос стал дорогим (инференс, RAG, tool-call) | Стоимость надо передавать *до* выполнения, иначе клиент не может планировать, а сервер не может защищаться |
| Агенты фанаутятся: один пользователь → сотни суб-агентов | Аутентификация не может стоить RTT на хоп; делегация должна быть офлайн |
| Ретраи — норма поведения, а не аномалия | Дедупликация одинаковой работы важнее любого байтового кэша |
| L7-атаки стали дешёвыми, а серверы дорогими | Отказ должен стоить дешевле обслуживания, а идентичность — быть выгодной |
| Collateral damage режет честных (CGNAT, облачный egress) | Ключ лимита не может быть IP-адресом |

### 1.2 Ограничения, которые я на себя наложил

- **Дёшево.** Никакой новой криптографии, никаких новых congestion-control. Всё, что на горячем пути, стоит ≤ 15 µs на одном ядре.
- **Быстро.** Один RTT на запрос даже на холодном соединении; 0-RTT через QUIC повторяет предыдущий полёт байт в байт.
- **Реализуемо.** Reference-реализация в этом репозитории проходит 41 инвариант.
- **Не ломает мир.** H3 остаётся; H4 добавляет семантику, которую H3 не может выразить, и деградирует в H3 через гейтвей.

## 2. Транспорт: почему эволюция QUIC, а не новый протокол

H4 = **семантический слой поверх QUIC**. Мы не трогаем то, что уже решено и отлажено годами:

| Уже есть в QUIC | Зачем это H4 |
|---|---|
| Мультиплексирование потоков без HOL-блокировки | Запрос = bidirectional stream, ответ = тот же поток |
| 0-RTT + возобновление | Повторный полёт запроса отправляется с первым пакетом — «холодный» запрос стоит 0 RTT в 90% случаев |
| Миграция соединения | Агент, переехавший из одного дата-центра в другой, не рвёт поток |
| Congestion control (CUBIC/BBR) | Не наша задача; ошибки здесь стоят дороже любых выигрышей |
| TLS 1.3 внутри | Идентичность H4 дополняет, а не заменяет транспортную |

Что H4 добавляет на уровне кадров — см. §3. Что **не** добавляет: собственный handshake, свою схему контроля перегрузки, своё управление потоком, свой формат пакетов.

> **Почему это важно для «дёшево и быстро».** Любая новая транспортная механика — это годы на отладку в реальном интернете (middleboxes, bufferbloat, PMTU-чёрные дыры). Единственный способ получить работающий протокол в 2026 году — не переизобретать транспорт, а исправить семантику.

Reference-реализация использует TLS-over-TCP с явным конвертом stream-id (`src/wire.js`) только потому, что в песочнице нет UDP-стека. Все байты после конверта — настоящие H4-кадры.

## 3. Формат на проводе

### 3.1 Varint

2-битный префикс, формы 1/2/4/8 байт — **сознательно совместимо с QUIC**. Переиспользование кодирования целых ничего не даёт, а совместимость даёт бесплатный путь: H4-кадры можно писать в QUIC-поток без переупаковки.

`writeVarint` / `readVarint` — `src/varint.js`. Нужен ещё zigzag для знаковых дельт (стоимость может быть отрицательной относительно предсказания).

### 3.2 Кадры

```
Frame = type(varint) | length(varint) | payload
```

| Тип | Имя | Направление | Смысл |
|---|---|---|---|
| `0x00` | `HEADERS` | оба | блок заголовков (§4) |
| `0x01` | `DATA` | оба | тело |
| `0x02` | **`INTENT`** | запрос | что клиент *имеет в виду* |
| `0x03` | **`COST`** | оба | экономика запроса/ответа |
| `0x04` | **`CAP`** | запрос | capability-токен |
| `0x05` | **`RESULT`** | ответ | единственный способ завершить запрос |
| `0x06` | **`RATE`** | ответ | квота и политика нагрузки |
| `0x07` | `CANCEL` | оба | отмена |
| `0x08` | `REJECT` | ответ | машиночитаемый отказ |
| `0x09` | `PATH` | обе | подсказки маршрутизации |
| `0x0a` | `ACCESS` | ответ | серверный лог в ответе (наблюдаемость) |
| `0x0b` | `PING`, `0x0c` `GOAWAY` | — | служебные |
| `0x0d` | **`HELLO`** | control-stream | начальное согласование (`proto`, `tableVersion`, `ratePolicy`, `sessionKey`) |

Три отличия от HTTP/3, каждое — следствие требования «быстро и дёшево»:

1. **Нет `SETTINGS`-разрастания.** Четыре вещи, которые действительно важны (идентичность, модель стоимости, политика лимитов, версия статической таблицы), идут в первом кадре один раз.
2. **Нет водопада «HEADERS, потом тело, потом трейлеры, потом, может быть, ошибка».** `HEADERS + INTENT + COST` всегда летят одним полётом — запрос завершается за один RTT даже на холодном соединении.
3. **Ответ — это `RESULT + RATE + COST + HEADERS + DATA`.** Фактическая стоимость сообщается *всегда*, даже на ошибку.

### 3.3 `INTENT`

```
mode(1B) | idem(bytes) | deadline_ms(varint) | cost_ceiling(varint)
        | max_shape(varint) | dedup_key(bytes)
```

- `mode`: `QUERY` / `MUTATE` / `SUBSCRIBE`.
- `deadline_ms` — сколько клиент готов ждать; сервер, не уложившийся, обязан вернуть `REJECT.DEFERRED`, а не «почти готово».
- `cost_ceiling` — потолок предсказанной стоимости. Сервер, чья оценка выше, **обязан отказать до выполнения** (`COST_REFUSED`). Это единственный способ дать клиенту бюджетный контроль без доверия к серверу.
- `max_shape` — агентская вещь: «ответ не больше N токенов/элементов». Дорогие ответы можно обрезать *до* генерации, а не после.
- `dedup_key` — ключ дедупликации для ретраев (§7).

### 3.4 `COST`

```
predicted(varint) | cost_class(u8) | effort_bits(u8) | budget_remaining(varint)
                  | value(varint) | token_budget(varint)
```

- `cost_class`: `CHEAP`=1 / `NORMAL`=5 / `EXPENSIVE`=60 единиц бюджета. Классы — это то, что делает лимит осмысленным: один запрос к кэшу и один вызов модели не могут стоить одинаково.
- `value` — сколько ответ, по мнению клиента, стоит. Из этого следует ключевое правило: **клиент не отправляет запрос, чья предсказанная цена выше ценности**. Агент, который не умеет оценивать ценность, — это агент, которого будут использовать как DoS-усилитель.
- `token_budget` — потолок на инференс, в токенах.

### 3.5 `RESULT`

```
status(varint) | cost_actual(varint) | cache(u8) | tokens(varint) | memo_reuse(varint)
               | wall_ms(varint) | cost_asym(zigzag varint) | flags(u8)
```

`cost_asym = actual − predicted`, **знаковое**. Это механизм обучения: клиент и промежуточные узлы копят асимметрию по маршрутам и корректируют свои предсказания. Без этого поля «умное предсказание цены» — это гадание; с ним — это обучаемая система, и она бесплатна (одно число в уже существующем кадре).

`cache`: `MISS` / `HIT` / `HIT_STALE` / `REVALIDATED` / `MEMO` (= работа выполнена для кого-то другого и переиспользована) / `COMPUTED`.

### 3.6 Коды отказа

`REJECT` вместо закрытия сокета — потому что закрытие сокета дороже (TLS-тирдаун, повторное рукопожатие) и бессмысленнее (клиент не знает, что делать).

| Код | Имя | Что делать клиенту |
|---|---|---|
| 1 | `RATE_LIMITED` | спать `retry_after_ms` |
| 2 | `BUDGET_EXHAUSTED` | пополнить бюджет, не ретраить |
| 3 | `EFFORT_REQUIRED` | решить PoE сложности `difficulty` и повторить |
| 4 | `CAP_INVALID` | обновить токен |
| 5 | `CAP_EXPIRED` | то же |
| 6 | `SCOPE_DENIED` | не ретраить, эскалировать |
| 7 | `AGENT_UNKNOWN` | представиться |
| 8 | `COST_REFUSED` | поднять потолок или сменить запрос |
| 9 | `MALFORMED` | баг в клиенте |
| 10 | `DEFERRED` | сервер перегружен, повторить позже |

Каждый отказ несёт `retry_after_ms` — это дешевле, чем заставлять клиента угадывать и долбить.

## 4. Сжатие заголовков: статическая таблица вместо состояния

**Решение: никакого per-connection dynamic table.** Каждый блок заголовков декодируется независимо.

Обоснование:

- QPACK/HPACK требуют состояния на соединение → память на каждое соединение + поверхность атаки (decompression bomb, рассинхронизация таблиц, восстановление после потери пакета).
- Выигрыш от динамической таблицы окупается только на длинных последовательностях *мало повторяющихся* заголовков. Агентский трафик наоборот: **чрезвычайно повторяющийся** — одни и те же имена моделей, тенантов, путей, MIME-типов.

Поэтому вместо состояния:

1. **Большая статическая таблица**, заточенная под агентов (`h4-agent`, `h4-agent-model`, `h4-tenant`, `h4-cap`, `h4-budget`, `h4-cost-class`, …). Точное совпадение пары — **1 байт**.
2. **Префиксный словарь значений**: `gpt-4o-mini` против `gpt-` → отправляется id префикса + суффикс; `https://api.` аналогично.
3. **Таблица — политический объект**: версия согласуется в первом кадре, значит сеть может поставлять таблицу v2 без слома совместимости. (Именно эта возможность и была бы невозможна с HPACK-состоянием.)
4. **Интернирование в реализации.** Профилирование показало: `TextEncoder.encode` стоит ~650 ns на строку и съедал 90% стоимости кодека. Требование к реализациям прямо в спеке: интернировать закодированные пары. После интернирования кодирование 8 заголовков: 5.2 µs → **1.7 µs**.

**Измерено** (`bench/bench.js`):

| случай | H4 | HTTP/1.1 текст | отношение |
|---|---|---|---|
| простой GET | 11 B | 72 B | 6.6× |
| агентский API-вызов (8 заголовков) | 48 B | 200 B | 4.2× |
| аутентифицированный агент | 52 B | 157 B | 3.0× |
| навигация браузера | 52 B | 171 B | 3.3× |

Декодирование: 845 ns на 8 заголовков, 1.18 M ops/s на ядре. Парсинг полного запроса (HEADERS+INTENT+COST+DATA, 79 байт) — 850 ns.

## 5. Идентичность: capability-токены с офлайн-делегацией

### 5.1 Проблема

Пользовательский агент порождает суб-агентов и tool-call'ы. Если каждый хоп требует round-trip к auth-сервису:

- **медленно** — RTT на каждом хопе, ровно на «денежном» пути;
- **дорого** — auth-сервис становится узким местом и новой целью для DDoS;
- **хрупко** — падение auth-сервиса останавливает всех.

### 5.2 Решение: macaroon-подобное сужение

```
root grant:   claims₀ ‖ Ed25519_issuer(claims₀)
attenuation:  linkᵢ = HMAC128(sigᵢ₋₁, claimsᵢ)
token:        ver ‖ keyId ‖ maxSubs ‖ claims₀ ‖ sig₀ ‖ (claims₁ ‖ link₁) ‖ …
claims:       caps ‖ expiresAt ‖ scope ‖ delegable ‖ tenant ‖ nonce
```

**Почему это безопасно, хотя соли HMAC публичны:**

- Власть даёт **только** подпись издателя над `claims₀`. Всё остальное — производные.
- Каждый хоп **обязан** сузить предыдущий: `caps ⊆ caps`, `expiresAt ≤ expiresAt`, `scope` — расширение пути. Расширение отклоняется на верификации, а не только на выпуске, поэтому держатель не может «отредактировать» токен.
- Значит, держатель может отдать только **меньше**, чем имеет. Классический инвариант «нет эскалации через делегацию».

### 5.3 Экономика проверки

| операция | измерено | вывод |
|---|---|---|
| Ed25519 verify | 141 µs (≈7k ops/s) | **нельзя** на горячем пути |
| HMAC-SHA256 | ~5 µs | можно |
| verify с кэшем корневой подписи (2 хопа) | **≈15 µs** | то, что нужно |

Кэш ключуется хэшем `sig₀`: одна Ed25519-проверка на **грант**, не на запрос. Тёплая проверка цепочки из 2 хопов — 15 µs (66k токенов/с на ядре).

### 5.4 `maxSubs` — подписанный потолок фанаута

Издатель подписывает, во сколько инстансов грант можно развернуть. Это решает неочевидную, но критичную проблему: **один утёкший токен не должен превращаться в ботнет с настоящей подписью**. Грант `maxSubs: 50` даёт оператору 50 долей квоты (честный фанаут), грант без `maxSubs` — одну долю (утечка не масштабируется).

### 5.5 Неочевидная деталь, найденная тестами

Два сиблинга, ответвлённые от одного гранта с **идентичными** claims, кодируются в идентичные байты → одинаковые токены → (поскольку ключ квоты — кончик цепочки) одна общая квота. Поэтому в claims обязателен `nonce`. Правило в спеке: **каждый инстанс = отдельный кончик цепочки**, иначе «квота на инстанс» невыразима.

## 6. H4-LIMIT: лимиты, которые считает клиент

### 6.1 Три ступени, каждая дешевле предыдущей

| | Ступень | Стоимость на сервере | Кто платит |
|---|---|---|---|
| 1 | **кооперативная квитанция** | ~5 µs (1 HMAC + счётчик) | клиент |
| 2 | **жёсткий per-identity bucket** | ~0.1 µs (1 int) | сервер (дёшево) |
| 3 | **proof-of-effort** | ~2 µs (1 SHA-256), **константа** | атакующий |

### 6.2 Ступень 1 — кооперативная квитанция

После рукопожатия сервер выдаёт клиенту сессионный ключ и **точную квоту**. Клиент на каждом запросе присылает `h4-rl: <receipt>,<mac128>`, где receipt — его собственный честный учёт: сколько единиц он потратил в окне и до какого момента он **сам себя заблокировал**.

Сервер: один HMAC + проверка монотонного nonce (защита от отката/реплея). Всё.

Смысл не в доверии. Смысл в том, что **честный клиент узнаёт о своём потолке раньше сервера**. Хорошо воспитанный клиент, исчерпавший бюджет, перестаёт отправлять — запрос не доходит до сети, и отбивать нечего.

Правило §6.4 (обязательное): **клиент не угадывает бюджет.** Если клиент додумывает квоту сам, его учёт расходится с серверным и тормозят именно честного — худший возможный исход для «кооперативной» схемы. Сервер обязан выдать квоту (`RATE` + provisioning в рукопожатии), клиент обязан её принять.

### 6.3 Ступень 2 — два ключа, а не один

Одно только per-instance ограничение бесполезно: клиент выдумывает instance-ID бесплатно. Одно только per-IP ограничение несправедливо: страдает весь CGNAT.

Поэтому H4 считает **оба** ключа:

- **instance** — ограничивает одного агента;
- **aggregate** — ограничивает размножение инстансов:
  - для анонимных — по сетевому адресу (с запасом `netMultiplier`, чтобы обычный NAT никогда не упирался);
  - для идентифицированных — по **гранту**, с потолком `budget × (1+bonus) × maxSubs` (подписанным издателем).

Верифицированная идентичность **выводит клиента из общего пула** — это и есть стимул её иметь, и причина, по которой честные не страдают за соседей.

### 6.4 Ступень 3 — цена вместо бана

При перегрузке сервер не банит, а **назначает цену**: `REJECT.EFFORT_REQUIRED` с `difficulty` бит. Клиент решает `SHA-256(challenge ‖ nonce)` с нужным числом ведущих нулей. Сервер проверяет одним хешем — **стоимость защиты константна**, стоимость атаки растёт как `2^difficulty`.

Задача **выводится**, а не хранится: `challenge = SHA-256(subject ‖ window)`. Флот edge-узлов разделяет вызовы с нулевым состоянием.

Измеренная экономика (одно ядро, SHA-256 = 0.5 M hash/s):

| сложность | хешей | время атакующего на запрос | стоимость защиты |
|---|---|---|---|
| 12 бит | 4 096 | 0.01 s | ~2 µs |
| 16 бит | 65 536 | 0.13 s | ~2 µs |
| 20 бит | 1 048 576 | 2.1 s | ~2 µs |
| 24 бита | 16 777 216 | 33.6 s | ~2 µs |

### 6.5 Результат: collateral damage

`bench/attack-sim.js` — честное сравнение: **та же суммарная ёмкость** у обоих подходов.

Сценарий: один origin; 50 честных агентов и 500 атакующих за общим пулом из 8 адресов (2 500 агентов на адрес — это и есть облачный egress / CGNAT); 20 000 запросов.

| | классический per-address limiter | HTTP/4 |
|---|---|---|
| честных обслужено | 300 (**12.0%**) | 2 500 (**100%**) |
| атакующих обслужено | 2 100 (12.0%) | 400 (**2.3%**) |
| атакующих отбито «ценой» | 0 | 17 100 |
| cost/запрос (включая HMAC и фрейминг) | — | 18.5 µs |

Честные: **12% → 100%**. Атакующие: **12% → 2.3%**, и 17 100 их запросов были оплачены их же CPU.

> Оговорка, которая должна быть в любой такой таблице: колонка CPU в симуляции сравнивает H4 (полный разбор запроса, HMAC, фрейминг) с голым счётчиком. Это не «H4 медленнее» — в L7-флуде честная метрика не скорость цикла, а кто получил обслуживание.

### 6.6 Отдельно: почему это снижает ущерб для всех

- **Честный клиент** не страдает за атакующего: у него своя идентичность и своя квота.
- **Атакующий** не получает пропорциональной доли: его отбивают по цене, а не по скорости.
- **Сеть** не носит мусор: кооперативная ступень отменяет запросы до отправки.
- **Origin** платит константу за отказ, а не за обслуживание.

## 7. Кэш, дедупликация и memo

Три вещи, которые агенты изменили в кэшировании:

1. Дорогая часть — часто **не байты, а инференс**. Два агента с семантически одинаковым запросом должны разделить один вызов модели.
2. Агенты ретраят агрессивно. Дедупликация **in-flight** работы стоит дороже любого байтового кэша.
3. Нагрузка рваная: кэш должен уметь сказать «не сейчас, спроси через 2 s», а не делать дорогую работу, которую придётся выбросить.

Реализация (`src/cache.js`):

- **Coalescing**: N одинаковых in-flight запросов стоят origin **одной** работы. При retry-storm это превращает O(N) в O(1). Инвариант: 100 одновременных одинаковых дорогих запросов → 1 вычисление (проверено тестом).
- **`CACHE.MEMO`**: клиент, чей запрос был обслужен чужой работой, получает `cost_actual = 1` и `memo_reuse`. Это сигнал «тебе повезло, не плати» — и одновременно данные для планировщика клиента.
- **Stale-while-revalidate под давлением**: при `pressure ≥ 96` отдаём устаревшее вместо пересчёта.
- **Учёт стоимости**: кэш-хит возвращает `cost_actual = 1` независимо от того, сколько стоил промах. Экономика кэша видна в протоколе, а не только в дашборде.

## 8. Порядок проверок на сервере

Это самый важный лист в документе: он определяет, сколько стоит атака.

| # | Проверка | Стоимость | Что предотвращает |
|---|---|---|---|
| 0 | декодирование кадров | ~100 ns | мусор, выход за границы буфера |
| 1 | верификация capability | ~15 µs (кэш корня) | чужой скоуп, подделка, истечение |
| 2 | лимит (квитанция → bucket → цена) | ~5 µs / ~0.1 µs | флуд, retry-storm |
| 3 | проверка скоупа пути | ~200 ns | доступ вне токена |
| 4 | потолок стоимости | ~200 ns | дорогая работа, которую не оплатят |
| 5 | дедупликация / coalescing | ~1 µs | повторная работа |
| 6 | **обработчик** | дорого | ← сюда не доходит ничего враждебного |

Правило: ни один отказ не должен уступать event loop. Уступка под нагрузкой — это способ превратить дешёвый отказ в дорогой.

Измерено (разброс между прогонами ±10%): обслуживание ≈15–17 µs (60–65k req/s на ядре), отказ ≈7 µs — **отказ в 2.2× дешевле обслуживания**. Это и есть свойство, из-за которого атака невыгодна.

## 9. Агент-специфичные возможности

Помимо базовой четвёрки, H4 несёт четыре вещи, которых нет в HTTP/3 и которые нужны именно агентам:

1. **`SUBSCRIBE` как метод первого класса.** Агент, ждущий события, не должен поллить. Один поток = одна подписка; `RATE` управляет частотой доставки, `DEADLINE` — временем жизни.
2. **`max_shape`.** «Дай не больше N токенов». Дорогой ответ обрезается **до** генерации, а не после. Прямая экономия на инференсе.
3. **`dedup_key`.** Семантика «я уже отправлял это, отдай результат той же работы» — на уровне протокола, а не приложения.
4. **`cost_asym` в каждом `RESULT`.** Каждый ответ — обучающий сигнал для предсказателя цены. Это делает «умное предсказание» самоулучшающимся без центрального координатора.

Плюс **наблюдаемость**: кадр `ACCESS` позволяет серверу вернуть клиенту его собственный лог (сколько стоил, что попало в кэш, в какой ступени лимита он был). Агент, который видит, почему его запрос дорог, оптимизируется сам.

## 10. Совместимость и внедрение

**Выбранная стратегия: gateway-first.**

```
   H4-клиент ──── H4 напрямую ────► H4-origin
       │
       └── fallback: H3 ──► edge-гейтвей H3↔H4 ──► H4-origin
   H3/2/1-клиент ── H3 ──► тот же гейтвей
```

Почему не «чистый лист»:

- Чистый лист даёт красивый протокол и ноль внедрения. Урок QUIC: семантика побеждает, когда её можно включить на одной стороне.
- Гейтвей позволяет origin'у получить эффект (дедупликация, лимиты, идентичность) **до** того, как клиенты обновятся.
- Деградация формализована: `:proto` в первом кадре; H4-специфичные возможности заявляются, а не предполагаются.

Фазы:

| Фаза | Что включено | Что уже даёт |
|---|---|---|
| 0 | гейтвей H3↔H4 | дедупликация и лимиты для всего существующего трафика |
| 1 | `COST`/`RESULT` в обе стороны | предсказание цены, обучение, бюджеты |
| 2 | `CAP` + делегация | офлайн-фанаут агентов, скоупы |
| 3 | кооперативные квитанции | клиентская самоблокировка, минус объём атак |
| 4 | PoE-цены под давлением | эластичная защита без банхаммера |

Что **не** надо делать: ломать H3, вводить обязательную идентичность (анонимный веб обязан остаться), требовать поддержки PoE для обычных людей (только под давлением и только для тех, кто уже исчерпал квоту).

## 11. Что мы сделали не так (журнал ошибок)

Спека без этого раздела — реклама. Все четыре ошибки ниже были найдены тестами и бенчмарками в процессе работы.

1. **Атакующий получил 100% обслуживания.** Первая версия лимитера ключевалась по заявленному клиентом instance-ID. Атакующий с 500 инстансов получил 500 квот. Вывод, попавший в §6.3: идентичность, которую клиент объявляет сам, бесплатна — нужны два ключа (инстанс + агрегат).

2. **Честные блокировали себя на 88%.** Клиент угадывал бюджет, сервер знал точный, учёт расходился. Вывод §6.4: квоту **выдаёт** сервер, клиент её **принимает**. Обе стороны должны считать в одних единицах.

3. **50 агентов с одним токеном схлопнулись в одну квоту.** Ключ квоты был кончиком цепочки, а два сиблинга с одинаковыми claims кодировались в одинаковые байты. Вывод §5.5: в claims обязателен `nonce`, «инстанс = отдельный кончик цепочки».

4. **Тесты врали.** Асинхронные проверки складывались в массив, а `process.exit()` в конце файла срабатывал раньше, чем они выполнялись: 27 «зелёных» тестов были только синхронными. После починки раннера сразу вылезли три реальных бага. Мораль для протокольной работы: **сначала докажи, что твой тест умеет падать.**

5. **Кэш подписи проверял только `sig0`, а `maxSubs` вообще не входил в подпись.** Ключевание `verifyCache` по одному `sha256(sig0)` позволяло подставить произвольные `claims0` под уже закэшированную подпись, а неподписанный `maxSubs` — раздуть квоту гранта правкой одного байта. Починено: Ed25519 подписывает `signedRoot = ver ‖ keyId ‖ maxSubs ‖ claims0`, а ключ кэша включает `(pubFp, signedRoot, sig0)`.

6. **Коллизия битовой маски в `headers.js` на индексах ≥ 32 и потеря кадров > 16 КБ в `wire.js`.** Бит `0x20` означал одновременно «есть префикс значения» и старший бит индекса таблицы `32..46` (`host`, `user-agent`, `h4-rl`), а `MessageParser` на клиенте пересоздавался на каждый чанк TLS. Починено 5-битным префиксным varint-индексом и единым парсером на соединение.

Плюс одна методологическая ошибка: первая версия бенчмарка сравнивала H4 с голым счётчиком и выдавала «2× быстрее». Число было бессмысленным; секция удалена, сравнение вынесено в отдельный честный сценарий.

## 12. Открытые вопросы

Честно о том, что не решено:

1. **Распределённый учёт квитанций.** Nonce монотонен в пределах сессии. Флот edge-узлов за балансировщиком потребует либо sticky-сессий, либо общего счётчика — это цена, которую надо измерить.
2. **Ценообразование PoE.** Сейчас `difficulty` — эвристика от `pressure` и числа нарушений. Нужна модель, связывающая сложность с реальной стоимостью запроса, иначе мы просто переносим задачу.
3. **Конфиденциальность.** `h4-agent-model` и `h4-tenant` — это fingerprint. Их надо либо шифровать на уровне приложения, либо явно объявить публичными в спеке.
4. **Кто платит за `value`.** Клиент объявляет ценность, но не платит за ложь. Нужен механизм (депозит, репутация), иначе `value` — просто ещё один бесплатный заголовок.
5. **Гейтвей и `cost_asym`.** Если гейтвей отвечает из кэша, чья асимметрия попадает в `RESULT`? Требуется явная семантика агрегации по цепочке.
6. **Формальный анализ.** Инвариант «сужение только вниз» доказан рассуждением и покрыт тестами, но не модельной проверкой. Для протокола такого класса нужен Tamarin/ProVerif.

## 14. Резюме в одном абзаце

HTTP/4 не пытается быть быстрее в байтах или в RTT — на этом поле HTTP/3 уже хорош. Он исправляет то, что сломалось при переходе от «человек кликает» к «агенты работают»: запрос теперь несёт **намерение, цену и проверяемую идентичность**, ответ несёт **фактическую стоимость и обучающий сигнал**, а лимиты считает **обе стороны**, поэтому честный клиент останавливается раньше, чем серверу придётся защищаться. Измеренный эффект в сценарии с общей CGNAT: честные с 12% до 100% обслуживания, атакующие с 12% до 2.3%, при константной стоимости защиты.
